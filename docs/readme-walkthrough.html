Friction points / things to add

1. Cold-start wait moderate

On a clean machine (empty Docker volumes) the backend container takes a noticeable interval between docker compose up exiting and /docs serving 200. A literal-minded reader who runs bun docker:dev then open http://localhost:3001/docs will see "connection refused" with no guidance.

Fix applied during this audit: README now says "wait for bnr-backend listening in the logs before hitting the API".

2. bun run dev was missing from the README minor

The root package.json exposes bun run dev (fans out to every workspace's dev via --filter '*') — the actual one-command happy path — but the README documented the longer two-step form (bun docker:dev + bun --cwd frontend dev) instead.

Fix applied during this audit: README "Run it" now leads with bun run dev, with the two-terminal form kept as an alternate workflow.

3. Frontend dev needs backend already up noted

The frontend README does say this ("Backend must be up (bun docker:dev from the repo root)"). Including this without forcing a reader to scroll back to root is the right call — kept.

What worked particularly well

  • Single root-README path. Three commands (bun install → bun docker:dev → bun --cwd frontend dev) get you a fully working system. No "fill these env vars first" detour.
  • Seed is idempotent and labelled. The log line "admin@bnr.local already exists — skipping" is exactly the kind of detail that lets a re-running engineer know what's happening.
  • Audit-verify endpoint is documented in the README itself, not just the design doc. The marquee feature is discoverable without diving into source.
  • Test command is single-step. bun --cwd backend test spins its own Postgres via testcontainers; no separate "start the DB first" instruction.
  • Limitations section — the README admits the password-hasher split, the disk blob store, the shared testcontainer, and the admin break-glass model up front. A reviewer skimming gets the same picture as a reviewer reading the design doc.
